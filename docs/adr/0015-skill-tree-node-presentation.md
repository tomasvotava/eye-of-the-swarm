# 0015 — Skill tree node presentation

**Status:** Accepted
**Date:** 2026-09-12

## Context

ADR 0014 keyed and stored 18 skill-tree icons (`SpriteKey.SKILL_{BRANCH}_{SUB_BRANCH}_{TIER}`),
each carrying `acquired`/`locked`/`normal` static variants, but built no consumer for them.
`SkillTreeScene` (`eye/gui/scenes/skilltree.py`) still renders every node through
`TextSkillTreeLeaf` — plain text, no art at all.

The delivered icon art has no fixed canvas. Sizes vary per node *and* per state:
`skill_self_attack_0/acquired.png` is 195×212 while that same node's `locked.png`/`normal.png`
are 167×184; the same pattern repeats across the catalog (`skill_self_defense_0`,
`skill_swarm_utility_2`, …). `SpriteIcon.render` (`eye/gui/widgets.py`) force-scales its source
surface to a square box via `pygame.transform.smoothscale(self._surface, (size, size))` — correct
for the effect/resource icons it serves today (uniformly ~210×210 per ADR 0011/0014), but it
would visibly squash or stretch this art if pointed at a skill icon directly.

`SkillNode` (`eye/skilltree/tree.py`) also carries no description field. PROJECT_BRIEF.md §9.6
calls for one: each skill should render with its name, effect list, and a description shown to
the player — a presentation-only addition, not a mechanic.

## Decision

- **`SkillNode` gains a `description: str = ""` field.** Catalog entries
  (`eye/skilltree/catalog.py`) get real flavor text — authored directly, not generated by this
  work, matching how this project's skill/item/enemy naming is already handled.
- **Skill icons render with an aspect-preserving "contain" fit, not a forced square scale.** A new
  helper (alongside `scale_sprite`/`scale_clip` in `eye/gui/animation.py`, or a dedicated
  code path in `eye/gui/widgets.py`) scales the source surface uniformly to fit inside a target
  box and centers it, rather than stretching to fill the box — the only approach that doesn't
  distort art whose size varies per node and per state. This is additive: `SpriteIcon`'s existing
  square-scale behavior is unchanged for its current consumers (`BuffIcon`/effect/resource icons,
  whose source art is already uniformly sized), since only the new skill-icon consumer opts into
  the contain-fit path.
- **`SkillIconVariant(StrEnum)` — `ACQUIRED`, `LOCKED`, `NORMAL`** — resolved via
  `atlas.get_variant_set(key, SkillIconVariant)`, filling the consumer slot ADR 0014 reserved but
  didn't build.
- **`SpriteSkillTreeLeaf`**, a new `SkillTreeLeaf` implementation rendering a node's icon (via the
  contain-fit helper) plus its name and a short effect-list line, becomes `SkillTreeScene`'s
  default `leaf_factory` in place of `TextSkillTreeLeaf`. This requires resizing the scene's grid
  geometry (`_CELL_WIDTH`/`_ROW_HEIGHT`/`_ROW_GAP`) to fit a taller per-node cell than today's
  single text line.
- **A selection-driven description inspector** shows a `Card` (`eye/gui/card.py`'s existing
  `Card`/`draw_card`, the same widget combat/exploration already use for buff/resource popups)
  for whichever node the cursor currently sits on, refreshed live as the cursor moves — no
  separate confirm keypress, since `SkillTreeScene` already tracks `_row`/`_col`. This depends on
  the icon helper and the new `description` field, but not on the grid-leaf replacement above; the
  two can land independently.

## Consequences

- `TextSkillTreeLeaf` stays in place as the plain-text fallback/test double, per its existing
  docstring — not removed.
- `SkillIconVariant` becomes `SpriteAtlas.get_variant_set`'s second real consumer alongside
  `IconVariant`, further confirming ADR 0011's generic-over-`TVariant` design rather than
  motivating a new mechanism (the same conclusion ADR 0014 drew in advance).
- Every one of the 18 `SKILL_*` `SpriteKey` directories already carries all three variant files
  today, so `get_variant_set`'s all-or-nothing contract (raises `ValueError` if any member is
  missing) is satisfiable as delivered. A future 19th skill added without all three variant files
  fails loudly at atlas-build time, not silently.
- Writing real flavor text for all 18 catalog entries is tracked as its own sub-issue's content,
  not specified by this ADR.
